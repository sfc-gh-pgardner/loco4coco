# The booth's model prompts

_Generated by `scripts/build_model_prompts.py` from `game/config.json` and `game/server.py`. Every prompt the booth sends to Cortex is below, filled against one example visitor so it reads as a single visit. Regenerate after changing config or the prompt code._

**The one rule that matters for porting:** the model only ever *picks and reflects*. The features, guides, listings and copy are ours - a closed set injected into the prompt as content - so the model chooses from them and speaks them back, but never invents a feature, a listing or a fact. The retrieval that builds the shortlist is deterministic (`game/context.py`), not a search service, so the same visitor input yields the same document.

Model: COMPLETE prompts run on `mistral-large2`; the Workshop's first turn runs on the warm agent / `cortex exec`. Placeholders in braces are filled from the visitor's own answers at runtime; the italic values below are the example.

The example visitor: **Priya, an NHS Trust, healthcare** - problem "we retype referral letters into our system by hand all day"; holds clinical notes and referral data on Azure; joining PubMed; residency EU.

## 5. The Workshop background fill (COMPLETE)

Runs silently after CoCo has spoken, while the visitor walks to the postbox. Fills the summary, first step, considerations and honest readiness score. Considerations are chosen by INDEX from a precomputed pool, so the prose is ours. Mirrors `refine_poc()` in `server.py`. `{candidates}` is the archetype's own pool from `archetypes.md`.

```text
You are helping shape a Snowflake proof of concept. Be concrete and never generic.

Person: Priya at an NHS Trust, Healthcare & Life Sciences.
They hold: Clinical notes & letters, Referral & waiting list data.
They will attach: PubMed Biomedical Research Corpus.
They asked the POC to: "a tool that reads our referral letters and extracts the fields we retype"
It is a 'extract-from-paperwork' build called 'Referral reader'.

Candidate considerations:
1. Define the fields precisely, including what an empty one means.
2. Decide your accuracy bar per field - a wrong total is not the same as a wrong date.
3. Plan the human check for low-confidence extractions before you go near production.
4. Layout drift breaks extraction quietly. Keep a sample set to re-test against.
5. Work out where the extracted data lands, and what happens when the same document arrives twice.

Return ONLY minified JSON, no prose, no code fence, with exactly these keys: {"summary": 2 sentences on what it does and why it matters to THEM, "first_step": one concrete first action, "considerations": array of exactly 3 integers, the numbers of the most relevant candidates above, "readiness": integer 1-5}
Score readiness strictly: only award 4 or 5 if they named specific data, a specific question and a specific user. Nobody sees the number, so be honest rather than kind.
```
